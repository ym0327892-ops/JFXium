# 通用编码技能

> 核心目标：改动小而准、推理透明、质量可控、结果可验证。

## 1) 谋定而后动

**不假设、不隐藏困惑，先暴露权衡。**

- 实现前明确假设；存在多种解释时先澄清，不静默选择
- 若有更简单路径，主动指出并说明理由
- 有不清楚的地方，停下来说明并询问

## 2) 极简至上

**用最少代码解决问题，不写推测性代码。**

- 不添加未请求的功能、灵活性或可配置性
- 不为单次使用场景制造抽象；明显过重就回退重写
- 200 行能用 50 行搞定的，重写

检验标准：一位高级工程师会说这过度复杂吗？如果是，简化。

## 3) 精准动刀

**只改必须改的部分，不顺手优化相邻代码。**

- 不重构没有损坏的东西，匹配现有风格
- 只清理由本次改动产生的孤儿代码；既有死代码只提示不删除
- 每一行修改都应可追溯到用户请求

## 4) 目标导向验证

**定义成功标准，循环验证直到完成。**

将任务转为可验证目标：
- "添加验证" → "为无效输入写测试，然后让它通过"
- "修复 bug" → "先写能复现的测试，再让它通过"
- "重构 X" → "确保重构前后测试都通过"

多步骤任务先给简要计划，每步附验证点。

## 5) 详注与日志（按需）

- 在关键逻辑处解释「为什么这样做」，记录决策权衡与前提假设
- 注释/日志遵循项目现有规范：按需、不过量、不冗余
- 中文注释优先（项目约定）

## 6) 通用代码质量约束（所有语言生效）

- 命名表达意图，避免 `data`、`tmp`、`mgr` 等空泛名
- 函数小而单一职责；需要用「并且」描述时考虑拆分
- 用卫语句/早返回控制嵌套，避免深层 if 金字塔
- 不留魔法数字/字符串，抽取具名常量
- 显式处理边界、空值与异常输入
- 异常不可吞；错误信息可定位，保留必要上下文
- 管理资源生命周期（连接、文件、句柄按时释放）
- 遵循 DRY，但遵守「三次法则」：重复三次再抽象

## 7) 通用安全与健壮性

- 在边界层校验外部输入
- 不硬编码密钥/口令；机密走环境变量或配置中心
- 防注入：参数化查询，正确转义输出
- 日志不输出敏感信息
- 新增依赖要显式说明：用途、license、维护状态

## 8) Java 倾向约定（优先但非强制）

- 分层职责清晰：controller/ui → service → repository/dao
- 构造器注入，不用字段注入
- 输入校验靠近边界层
- DTO/VO 与持久化实体分离
- JUnit 5 优先；仅在必要隔离场景使用 mock

## 9) JavaFX 约定

- UI 逻辑与业务逻辑分离，Controller 保持轻量
- 耗时操作放到 UI 线程之外执行
- UI 更新回到 JavaFX Application Thread
- 以可用性和一致性优先

## 10) 完成定义（DoD）

任务完成前至少满足：
1. 每一处改动都可追溯到用户需求
2. 运行项目真实验证命令（构建/测试/lint）并通过
3. 至少完成一条验证路径
4. 交付说明包含：改了什么、为什么改、影响范围、剩余风险

## 11) 非目标（避免）

- 未请求的框架迁移
- 未请求的大规模结构调整或重命名
- 与当前任务无关的依赖升级
- 面向未来假设的过度架构设计

## 12) 常见误区

| 误区 | 后果 | 正确做法 |
|------|------|----------|
| "我猜用户想要这个" | 返工 | 明确需求再动手 |
| "先写着，以后可能用上" | 死代码 | 只写当前需要的 |
| "顺手优化一下" | 引入 Bug | 克制，聚焦任务 |
| "应该没问题" | 上线事故 | 定义可验证的成功标准 |
