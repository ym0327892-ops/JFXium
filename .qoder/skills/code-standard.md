# 通用编码技能（JFXium 特化版）

> 核心目标：改动小而准、推理透明、质量可控、结果可验证。
> 写 JFXium 组件时：**必读 §9 + §10**。

## 1) 触发条件

在以下场景启用本技能：

- 开发新功能 / 实现需求
- 修复 Bug
- 重构现有代码
- 代码审查与质量改进
- 性能或可读性优化
- 新增或补齐测试
- 排查线上问题

常见触发词：实现、写功能、fix bug、refactor、review、优化、add test、API、service、Java、JavaFX。

## 2) 核心准则（先想后写）

源自 Karpathy 对 LLM 编码常见误区的观察。偏向谨慎而非速度；琐碎任务可自行判断。

### 2.1 谋定而后动
- 不假设、不隐藏困惑，先暴露权衡
- 实现前明确假设；存在多种解释时先澄清，不静默选择
- 若有更简单路径，主动指出并说明理由

### 2.2 极简至上
- 用最少代码解决当前问题，不写推测性代码
- 不添加未请求的功能、灵活性或可配置性
- 不为单次使用场景制造抽象；明显过重就回退重写

### 2.3 精准动刀
- 只改必须改的部分，不顺手优化相邻代码、注释或格式
- 不重构没有损坏的东西，匹配现有风格
- 只清理由本次改动产生的孤儿代码；既有死代码只提示不删除
- 检验标准：每一行修改都可追溯到用户请求

### 2.4 目标导向验证
- 把任务转成可验证目标：「修 bug」→「先写能复现的测试，再让它通过」
- 多步骤任务先给简要计划，并在每步附验证点
- 持续循环直到成功标准满足，而非「看起来能跑」

### 2.5 详注与日志（按需）
- 在关键逻辑处解释「为什么这样做」，记录决策权衡与前提假设
- 注释 / 日志遵循项目现有规范：默认按需、不过量、不冗余
- **默认推荐中文注释**（团队统一、可读性优先）
- 仅在用户明确要求可追溯记录时，增加更详细的中文注释或日志
- 日志聚焦关键路径的输入、决策点、结果，不堆砌噪音

## 3) 通用代码质量约束（所有语言生效）

- 命名表达意图，避免 `data`、`tmp`、`mgr` 等空泛名
- 函数小而单一职责；需要用「并且」描述时考虑拆分
- 用卫语句 / 早返回控制嵌套，避免深层 if 金字塔
- 不留魔法数字 / 字符串，抽取具名常量
- 显式处理边界、空值与异常输入，不依赖隐式默认
- 异常不可吞；错误信息可定位，保留必要上下文
- 管理资源生命周期（连接、文件、句柄按时释放）
- 涉及共享状态 / 并发时，明确线程安全边界
- 遵循 DRY，但遵守「三次法则」：重复三次再抽象，避免过早抽象

## 4) 通用安全与健壮性（所有语言生效）

- 在边界层（接口 / UI 输入）校验外部输入
- 不硬编码密钥 / 口令；机密走环境变量或配置中心
- 防注入：使用参数化查询，正确转义输出
- 日志与报错不输出敏感信息（密钥、令牌、个人信息）
- 对外暴露的资源 ID 避免可枚举的自增值
- 新增依赖要显式说明：用途、为何现有栈不满足、license、维护状态

## 5) Java 倾向约定（优先但非强制）

当使用 Java 时，优先遵循：

- 分层职责清晰：controller/ui -> service -> repository/dao
- 构造器注入，不用字段注入
- 输入校验靠近边界层（API / UI 输入层）
- 需要时将 DTO / VO 与持久化实体分离，不直接暴露内部模型
- 倾向局部改动，避免跨层大范围联动重写
- 测试优先遵循 JUnit 5；仅在必要隔离场景使用 mock

## 6) JavaFX 约定

- UI 逻辑与业务逻辑分离，Controller 保持轻量
- 业务行为尽量下沉到 service
- 耗时操作放到 UI 线程之外执行
- UI 更新回到 JavaFX Application Thread
- 以可用性和一致性优先，不做无请求的外观大改

## 7) 完成定义（DoD）

任务完成前至少满足：

1. 每一处改动都可追溯到用户需求
2. 运行项目真实的验证命令（构建 / 测试 / lint，按项目实际配置）并通过
3. 至少完成一条验证路径（测试 / 构建 / 复现 / 关键路径手验）
4. 交付说明包含：改了什么、为什么改、影响范围、剩余风险

## 8) 非目标（避免）

- 未请求的框架迁移
- 未请求的大规模结构调整、重命名或格式化
- 与当前任务无关的依赖升级
- 面向未来假设的过度架构设计

## 9) JFXium 特定约定（写组件代码必读）

JFXium 核心栈：Java 21 + JavaFX 21.0.6 + LESS（jlessc 编译）+ Builder 模式。
写 JFXium 组件时，必须遵守以下 5 条核心契约（完整红线见 `.qoder/rules/red-lines.md`）：

1. **Builder 模式 + 返回类型诚实**：`XxxAnt.create().xxx().build()` 返回什么就是什么，不包不装
2. **LESS 主题优先**：颜色 / CSS 走 styleClass + LESS，**严禁** `setStyle()` 写颜色 / px
3. **jfx- 前缀**：新建 styleClass 必须 `jfx-` 前缀，避免与 modena 冲突
4. **CSS 交互状态规范**：用 `:pressed` / `:armed` / `:focused` / `-fx-effect: dropshadow(...)`，禁用 `:active` / `:focus` / `box-shadow` / `-fx-transition`（动画类除外）
5. **exports 同步**：新增 public 类必须同步 `module-info.java` 的 exports 声明

## 10) JFXium 参考模板（按需加载）

JFXium 已有的项目特定 skill / rule，**按需加载**，避免臆造 API：

| 文件 | 类型 | 何时加载 |
|------|------|----------|
| `.qoder/rules/red-lines.md` | always-on | 始终生效，致命红线 |
| `.qoder/skills/project-constraints.md` | 按需 | 改组件样式 / 颜色 / 交互状态前 |
| `.qoder/skills/component-pattern.md` | 按需 | 新建 / 重构组件前 |
| `.qoder/skills/workflow.md` | 按需 | 执行构建 / 测试 / 发布时 |
